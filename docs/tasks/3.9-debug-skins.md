### 3. Contract feedback (missing / ambiguous / awkward)
The contract is genuinely sufficient — I never had to invent anything. The friction points:

1. **`onBackPressed()` vs. AppSkin rule 2 is a real tension.** Rule 2 says "Hold durable state in a `rememberSaveable` or a ViewModel, not in a field," but `onBackPressed()` is a plain, non-`@Composable` method that cannot reach a `rememberSaveable`. So a 1-level back stack *must* live in a field the method can see. I used `mutableStateOf` as the task permitted, but for production skins this contract should either (a) hand the skin a small navigation holder/`SnapshotStateList` via `SkinSession`, or (b) make `onBackPressed` receive a snapshot-holder param, or (c) explicitly bless a thin ViewModel. Right now the guidance contradicts the method signature.

2. **"Material3" is listed as a pinned version but is not a dependency of the `skin` module** (`skin/build.gradle` declares only `compose-runtime`, `compose-ui`, `paging-common`, `paging-compose`, coroutines). Since build.gradle must not be touched, skins physically cannot use `MaterialTheme`, `Text`, `Button`, `Scaffold`, etc. I built everything from `androidx.compose.foundation` + `BasicText`. This is workable but is worth a decision: either add a theme/text primitives dependency to the module, or document that skins render raw foundation UI.

3. **Two overlapping load signals with no guidance.** The contract exposes both the whole-library `session.library.loadState` (indexing: `Scanning/Failed/Ready`) and the per-list `LazyPagingItems.loadState` (page refresh/append). For a root list these both go `Loading`-ish at start, so a skin has to decide which to trust. I keyed off `library.loadState` (as required) and ignored paging's own `loadState`; the contract could note the intended precedence.

4. **`Scanning(loaded: Int?, explored: Int?)` — both nullable with no stated meaning.** "loaded" and "explored" are self-describing in English, but there's no doc on units or direction (explored of what — directories? files?), and rendering `null`s requires ugly `"null"` guards in strings. Minor, but a one-line doc on each field would remove guesswork.

5. **`openAppSettings` doc says a skin "SHOULD" surface it** — good, I followed it. No issue, just noting it fired correctly.

### 4. What I was tempted to reach into the engine for
Nothing from `org.oxycblt.*` — the contract covered everything. The only reach I felt was for **`androidx.compose.material3`** (`Text`/`Button`/`Scaffold`) and **`androidx.lifecycle.compose.collectAsStateWithLifecycle`**, both of which are engine-independent but simply absent from this module's dependency set (as the task warned). Not having a hosted `ViewModel` to stash navigation state was the single most awkward gap (see point 1), and a small shared nav holder in the contract would have removed the one hacky bit of the implementation.
